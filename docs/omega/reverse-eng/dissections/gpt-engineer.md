## 4. Traduction en plugins

- `ge-patch-validate` : patch-validate → `PatchValidator` → `plugins/patch-validate` (plugin, planned, **L**) — **le meilleur apport de tout le dépôt**. Un LLM qui écrit un diff se trompe de numéros de ligne, oublie des lignes, invente des commentaires, ajoute des lignes fantômes ; gpt-engineer ne se contente pas de rejeter, il **répare** en mesurant la similarité de fréquence de caractères et en recalculant les compteurs de hunk. Aucun harnais moderne que nous avons disséqué ne fait ça ; à porter en priorité, avec de vrais tests de non-régression (les fixtures de `tests/core/test_chat_to_files.py:228-288` et `tests/core/test_salvage_correct_hunks.py:46-62` sont directement réutilisables comme oracle).
- `ge-repair-loop` : self-healing → `RepairLoop` → `plugins/repair-loop` (plugin, planned, M) — le motif « exécuter → réinjecter l'erreur → patcher → reboucler » est exactement notre `repair` post-tool, mais **borné et budgété** : gpt-engineer plafonne à 10 essais *sans limite de temps* (`timed_out = False` est une constante, `tools/custom_steps.py:97`, et `communicate()` est appelé sans timeout). Nous devons ajouter timeout + budget tokens par boucle.
- `ge-clarify-loop` : clarify-loop → `ClarificationLoop` → `plugins/clarify-loop` (plugin, planned, S) — trois règles à copier : **une seule question par tour**, sortie sur marqueur explicite (« Nothing to clarify »), et `c` = « fais tes hypothèses **et énonce-les** avant de commencer ». Le transcript de clarification est réinjecté dans le prompt système de génération (`tools/custom_steps.py:181-190`) : la spécification n'est donc jamais perdue.
- `ge-context-file-picker` : context-engine → `ContextBudget` → `plugins/context-file-picker` (plugin, planned, M) — sélection du contexte **par un fichier versionnable** plutôt que par heuristique. Le TOML commenté (« `# » = désélectionné ») est un format quasi dichotome, lisible par un humain et diffable en PR. Complément indispensable à notre `ContextBudget`/`ToolSurfaceIndex`, qui sont automatiques.
- `ge-exec-confirm-preview` : permission-policy → `PermissionPolicy` → `omega-sandbox::ApprovalQueue` (plugin, **adopted**, S) — l'adaptateur existe ; ce qu'il faut ajouter : **deux points d'arrêt distincts** (exécuter / appliquer) et surtout le refus qui *restaure* l'état précédent (`applications/cli/main.py:539-540`), avec le diff unified coloré comme pièce à conviction (`compare`, `:203-240`).
- `ge-preprompt-library` : skill-store → `SkillStore` → `omega-context::SkillIndex` (plugin, **adopted**, S) — le `SkillIndex` sait déjà lister/charger des fichiers de prompt ; il manque la **composition par nom** (`roadmap + generate + philosophy`) et la **substitution de jeton** (`FILE_FORMAT`), plus la sémantique « surcharge projet sans écraser les défauts » (`applications/cli/main.py:173-200`). Extrapolation notable : *ajouter un fichier dans `preprompts/` = ajouter une capacité*, sans toucher au code.
- `ge-token-cost-meter` : telemetry-sink → `TelemetrySink` → `omega-otel::{StdoutSink,FileSink}Sink` (plugin, **adopted**, S) — le metering existe et est même plus fin que nous (`step_name` = nom de la fonction d'étape). Le gain à copier : le coût doit venir du `ModelRecord` (notre `cost_input_per_1m`/`cost_output_per_1m`), pas d'une table de prix figée dans une dépendance tierce comme le fait `get_openai_token_cost_for_model`.
- `ge-entrypoint-synthesis` : sandbox-backend → `SandboxBackend` → `omega-sandbox::LocalSandboxBackend` (plugin, **adopted**, M) — `run` existe ; à porter : l'upload d'un arbre de fichiers dans le bac à sable et la synthèse du script d'exécution par le modèle (avec ses interdits : pas de `sudo`, pas d'installation globale, pas de placeholder — `preprompts/entrypoint`).
- `ge-project-toml-config` : config-source → `ConfigSource` → `omega-config` (plugin, **adopted**, S) — l'adaptateur de couches existe ; à ajouter : l'**écriture non destructive** (on ne réécrit que les clés présentes ou différentes du défaut, ce qui préserve commentaires et clés inconnues — `core/project_config.py:122-151`) et le schéma `[run] build/test/lint/format`.
- `ge-benchmark-harness` : eval-harness → `BenchmarkRunner` → `omega-eval-harness` (plugin, planned, **L**) — le protocole d'évaluation d'agents est minimal et réutilisable : `Assertable{files, env, stdout, stderr}` + `Assertion = Callable[[Assertable], bool]`, exécution dans un environnement **neuf** à chaque assertion pour éviter les effets de bord (`gpt_engineer/benchmark/benchmarks/mbpp/load.py:37-49`), et chargement d'un agent tiers par `importlib` + `default_config_agent()`. C'est un socle de banc d'essai inter-harnais bon marché.
- `ge-step-pipeline` : agent-loop → `AgentLoop` → `plugins/agent-loop` (plugin, planned, M) — l'intérêt est **négatif** mais pédagogique : montrer qu'un agent « prompt → code → run → repair » tient en 400 lignes et 4 appels LLM, et que la valeur est dans le *format de patch*, pas dans la boucle.
- `ge-numbered-file-context` / `ge-multimodal-prompt` : context-engine → `ContextEngine` → `omega-context::DefaultContextEngine` (plugin, **adopted**) — la projection numérotée est le contrat qui rend toute la validation de hunks possible ; le canal multimodal image manque chez nous, et surtout le **drop silencieux** des images non supportées (`applications/cli/main.py:479-480`) est un défaut à ne pas reproduire — Omega doit émettre un événement.
- `ge-disk-memory-logs` : memory-store → `MemoryStore` → `plugins/memory-fs` (plugin, planned, S) — le port `MemoryStore` existe **sans aucun adaptateur** dans le dépôt Omega ; l'idée minimale à reprendre est le log horodaté par étape avec garde anti-traversée (`../`) et archive datée.
- `ge-git-stage-guard` : vcs-snapshot → `SnapshotStore` → `plugins/vcs-stage` (plugin, planned, S) — protection anti-destruction avant écriture ; chez nous il manque le concept même de point de retour (pas de commit, pas de message : à Omega ce serait un `DurableEvent` + un worktree).
- `ge-clarify` / `ge-code-emitter` / `ge-patch-apply` / `ge-lint-before-context` : petits greffons (`S`), à traiter dans le lot.

## 5. Écarté

- **`ge-consent-telemetry` (rejected).** L'envoi du prompt, du modèle, de la configuration **et de l'intégralité des logs (= tout le code écrit)** vers `gptengineerezm.dataplane.rudderstack.com` avec une `write_key` en dur dans le code (`applications/cli/collect.py:53-62`) est incompatible avec nos règles : le calcul va au système, pas chez un tiers, et la provenance reste locale (`omega-otel::Provenance`). Le consentement explicite (`.gpte_consent`) et la revue en trois questions (`ran` / `perfect` / `works` + commentaire) sont en revanche excellents : on les garde comme **journal local de scoring**, jamais comme exfiltration.
- **`ClipboardAI` non repris.** `core/ai.py:386-437` : le « LLM » est l'utilisateur qui colle une réponse dans le presse-papier. Sympathique pour l.debug hors ligne, hors périmètre produit.
- **Le choix de backend codé en dur dans le runtime Python/langchain.** `AI` est le seul endroit qui parle à un LLM, mais il **hardcode** le choix du backend par heuristique de nom de modèle (`azure_endpoint` → Azure, `"claude"` → Anthropic, `vision` → OpenAI avec `max_tokens=4096`, `core/ai.py:330-379`). Nous ne reprenons pas cette mécanique : chez Omega c'est `omega-registry` + `omega-router` qui décident, et le « model/provider en dur » est explicitement interdit par `RULES-OMEGA`. Seule la partie « résilience d'appel » (backoff exponentiel sur `RateLimitError`, 7 essais / 45 s, `core/ai.py:253-287`) mérite d'être rejouée sur le port `Provider` — en `async`, avec jitter.
- **Le « mode lite »** (`--lite`, `tools/custom_steps.py:198-233`) ne consiste qu'à passer le `file_format` en guise de prompt système : c'est un *workaround* pour les petits modèles ouverts (`docs/open_models.md`), pas une fonctionnalité. Il est conservé dans `ge-clarify-loop`/modes CLI comme simple option.
- **L'entrée `gpte_test_application`** (`pyproject.toml:87`) pointe vers `tests.caching_main:app`, fichier absent du clone : entrée morte, à signaler comme dette.
