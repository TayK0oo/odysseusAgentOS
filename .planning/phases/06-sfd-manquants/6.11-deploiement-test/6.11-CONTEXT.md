# Phase 6.11 — Déploiement & Test E2E : CONTEXT

**Gathered:** 2026-07-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Déployer l'intégralité d'Agent OS sur un environnement VPS-ready, exécuter un test de bout en bout sur un projet réel (backup automatisé), et valider que chaque module SFD fonctionne en conditions réelles. Le système doit suivre les bonnes pratiques du guide de développement (cycle de vie complet : avant-projet → conception → setup → développement → qualité → déploiement → maintenance).

Cette phase produit : un script de déploiement, un script de test E2E, un workflow CI/CD, et un rapport de validation.
</domain>

<decisions>
## Implementation Decisions

### Infrastructure de déploiement
- **Docker Compose enrichi** — profil `production` avec Traefik + Let's Encrypt déjà présents
- **VPS-ready** : un fichier `deploy/vps/docker-compose.prod.yml` avec toutes les configs nécessaires
- **Sandboxing** : gVisor (déjà dans la stack), phase-lock, permissions granulaires
- **L'agent peut modifier le docker-compose.yml** pour ajouter/retirer des services (liberté d'évolution)
- Profils Docker : `default` (dev local), `production` (VPS), `minimal` (test CI)

### Périmètre des tests
- **Full stack** : HTTP, cockpit UI, phase bar, SSE events, mémoire, préférences, classification, sécurité, discovery
- **189 tests unitaires existants** + nouveaux tests E2E
- Vérification visuelle du cockpit (phase bar, progression 7 phases)
- Vérification des use cases SFD via le projet backup automatisé

### Automatisation
- **Script local** : `scripts/test-e2e.sh` — lance Docker Compose → attend health → curl endpoints → pytest → rapport
- **CI/CD** : `.github/workflows/e2e.yml` — exécute les tests sur push, avec quality gates
- **Quality gates** : lint OK, 100% tests SFD passent, couverture minimale

### Use case de démonstration
- **Projet "backup automatisé"** — l'utilisateur dit "Crée un système de backup automatisé pour mon serveur"
- Le système suit tout le cycle de vie du guide de bonnes pratiques :
  1. **Avant-projet** (CLASSIFY) : analyser le besoin, cadrer
  2. **Conception** (KNOW+PLAN) : specs, architecture, ADR
  3. **Initialisation** (PLAN) : repo, CI/CD, environnements
  4. **Développement** (BUILD) : code, tests, doc
  5. **Qualité** (QUALITY) : tests, lint, sécurité
  6. **Déploiement** (BUILD) : release, changelog
  7. **Maintenance** (MEMORY_OBSERVE) : leçons apprises, mémoire

### Mode Chat vs Agent
- **Détection automatique** : le système analyse la requête — si elle contient des signaux de projet (créer, build, déployer, implémenter, refactorer...), passage en mode agent automatiquement
- **Switch manuel** : l'utilisateur peut cliquer sur le bouton Agent/Chat dans l'UI (déjà existant)
- **Mode Chat** : pas de phases, pas de planification, réponse directe — pas de bus de pensée
- **Mode Agent** : bus de pensée actif, 7 phases, tous les modules SFD activés, suit le guide de bonnes pratiques

### Checklist de validation E2E
Chaque étape du use case backup automatisé est vérifiée :

1. [ ] **CLASSIFY** — le système détecte que c'est un projet (pas du quick chat)
2. [ ] **KNOW** — recherche conversations passées, charge la mémoire, les préférences
3. [ ] **PLAN** — décompose en objectifs, crée le plan YAML
4. [ ] **BUILD** — exécute avec outils, exécution durable active
5. [ ] **QUALITY** — exécute les tests, vérifie les critères
6. [ ] **AUTOEVAL** — auto-évalue le résultat
7. [ ] **MEMORY_OBSERVE** — écrit dans la mémoire avec provenance
8. [ ] **Cockpit UI** — phase bar progresse C→K→P→B→Q→A→M
9. [ ] **Préférences** — appliquées (format, ton, langue)
10. [ ] **Mémoire** — faits tagués [stated]/[observed], pas de données protégées
11. [ ] **Sécurité** — pas d'injection, pas de contenu bloqué
12. [ ] **Sortie visuelle** — diagrammes si pertinents

<specifics>
## Specific Ideas

- Le guide de bonnes pratiques donne un cadre complet : le système doit le suivre quand il est en mode agent
- Le projet backup automatisé doit servir de "golden path" — si ce use case passe, tout le reste est solide
- Le script test-e2e.sh doit pouvoir tourner en local (dev) et en CI (GitHub Actions)
- La détection chat/agent doit être explicite : l'utilisateur voit "Mode Agent activé — le système va planifier et exécuter"
</specifics>
